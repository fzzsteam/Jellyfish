# 用户积分计费设计文档

**日期：** 2026-06-22  
**状态：** 已确认，待实现

---

## 背景

Jellyfish 已支持文本、图片和视频模型调用，但当前没有统一的用户额度控制、调用前计价、执行中冻结、成功扣费和失败返还机制。管理员也无法为用户配置积分额度或审计积分变化。

本次改造引入按用户归属的积分体系。积分只针对实际调用大模型或生成供应商的接口收取；普通 CRUD、提示词预览、任务查询、素材编辑和其他本地逻辑不计费。

## 目标

- 管理员可通过正数或负数充值修改用户积分。
- 每个模型使用统一的 `unit_points` 字段配置积分单价。
- 文本按次、图片按张、视频按秒和分辨率计费。
- 所有模型调用统一先冻结，成功后消费，失败或取消后解冻。
- 积分不足时阻止供应商调用，并返回可用积分、本次需要和差额。
- 用户可查看积分余额、冻结金额及完整消费和充值明细。
- 前端在执行前展示确定的“将消耗 X 积分”。
- Redis 用户级原子锁与数据库事务、行锁共同保证并发安全。
- 为未来用户自助充值预留来源字段，但首期不开放入口。

## 非目标

- 不引入团队、项目或组织共享积分。
- 不建立独立的业务积分账户体系，积分直接归属用户。
- 不引入模型价格倍率。
- 不按图片或视频宽高比计费。
- 首期单次生成数量固定为 `1`，不提供批量生成计费。
- 首期不开放支付渠道和用户自助充值。
- 不新增独立的 `adjust` 流水类型。

## 核心术语

| 术语 | 说明 |
|---|---|
| 总积分 `balance` | 用户当前持有的积分总额，包含已冻结但尚未结算的积分 |
| 冻结积分 `frozen` | 已为运行中模型调用预留、暂不可再次使用的积分 |
| 可用积分 `available` | `balance - frozen` |
| 试算 `quote` | 根据最终模型及调用参数计算本次确定价格，不修改余额 |
| 计费编号 `billing_id` | 一次模型调用计费生命周期的唯一标识 |
| 计价快照 | 调用时的模型价格、分辨率系数、时长等不可变审计数据 |

## 1. 计费规则

### 1.1 模型价格

`models` 表新增统一字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `unit_points` | 非负整数 | 模型基础积分单价；具体单位由 `category` 决定 |

不同模型类别的字段语义：

| 模型类别 | `unit_points` 单位 |
|---|---|
| `text` | 积分/次 |
| `image` | 积分/张 |
| `video` | 积分/秒 |

`unit_points` 必须为非负整数。值为 `0` 表示允许免费调用，不能使用空值隐式表达免费。

### 1.2 计算公式

```text
文本积分 = unit_points

图片积分 = ceil(unit_points × resolution_factor × generation_count)

视频积分 = ceil(unit_points × duration_seconds × resolution_factor × generation_count)
```

首期 `generation_count` 固定为 `1`。所有结果以整数积分表示，并统一向上取整。

### 1.3 分辨率系数

分辨率系数由后端计费模块集中维护，前端和供应商适配器不得重复定义。首期固定为：

| 类型 | 分辨率 | 系数 |
|---|---|---|
| 图片 | 当前唯一规格 | `1.0` |
| 视频 | `720p` | `1.0` |
| 视频 | `1080p` | `2.0` |

首期图片只有一个有效规格，因此图片分辨率系数固定为 `1.0`。视频只允许 `720p` 和 `1080p` 参与计费；大小写由后端规范化。未知分辨率必须拒绝计费和调用，不能静默使用默认系数。未来增加新规格时，必须同步增加明确系数。

首期图片只根据生成数量变化，唯一规格的系数恒为 `1.0`；视频根据生成数量、时长和分辨率变化。宽高比不参与计费。

### 1.4 确定价格

首期所有计费参数在调用前均已确定，因此界面展示的是确定价格，不是模糊估算。界面文案使用“将消耗 X 积分”。

如果试算后模型、模型价格或计费参数发生变化，正式提交不得直接按新价格扣费，而应返回价格变化错误，让用户看到新价格并重新确认。

## 2. 数据模型

### 2.1 `user_points`

积分直接跟随用户，本表是用户积分状态的物化记录，不代表额外的业务账户。

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | FK + unique | 用户 ID，每个用户仅一行 |
| `balance` | bigint, default 0 | 总积分 |
| `frozen` | bigint, default 0 | 冻结积分 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

约束：

```text
balance >= 0
frozen >= 0
frozen <= balance
available = balance - frozen
```

新用户创建时同步初始化积分记录，初始值为 `0`。读取历史用户时若记录不存在，可由迁移统一补齐；业务运行时不依赖无审计记录的隐式赠送。

### 2.2 `point_transactions`

流水只追加，不修改历史记录。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | 主键 | 流水 ID |
| `user_id` | FK | 积分所属用户 |
| `type` | enum | `recharge`、`freeze`、`consume`、`unfreeze` |
| `amount` | bigint | 本次操作积分；充值可正可负，其余类型使用正数 |
| `balance_after` | bigint | 操作后的总积分 |
| `frozen_after` | bigint | 操作后的冻结积分 |
| `source` | string/enum | `admin`、`llm`，未来可增加 `self_service` |
| `billing_id` | string, nullable | 模型调用计费编号 |
| `business_type` | string, nullable | 文本、图片、视频及具体业务动作 |
| `business_id` | string, nullable | 任务或业务对象 ID |
| `model_id` | FK, nullable | 实际使用的模型 ID |
| `pricing_snapshot` | JSON, nullable | 本次计价参数快照 |
| `remark` | text, nullable | 充值或异常处理备注 |
| `created_by` | FK, nullable | 操作人；模型调用可为空或记录当前用户 |
| `created_at` | datetime | 创建时间 |

模型调用流水增加唯一约束：

```text
UNIQUE(billing_id, type)
```

该约束防止同一阶段重复执行。结算时必须锁定对应 `freeze` 流水并检查是否已存在 `consume` 或 `unfreeze`，确保二者互斥。

### 2.3 计价快照

`pricing_snapshot` 至少保存：

```json
{
  "model_id": "model-123",
  "model_category": "video",
  "unit_points": 10,
  "resolution": "1080p",
  "resolution_factor": 2.0,
  "duration_seconds": 10,
  "generation_count": 1,
  "required_points": 200
}
```

文本和图片不适用的字段省略。模型价格修改后，历史明细始终展示快照，不反查当前价格重算。

## 3. 模型解析与试算

### 3.1 默认模型处理

前端不需要获取或补传默认模型 ID。试算接口和正式调用接口均允许 `model_id` 为空，并复用同一个后端模型解析器：

1. `model_id` 有值时，校验模型归属和类别后使用显式模型。
2. `model_id` 为空时，根据当前用户和所需类别解析默认模型。
3. 使用解析后的模型执行计价或供应商调用。

当前调用边界：

- 文本生成使用当前用户默认文本模型。
- 图片生成优先使用用户选择的模型，未指定时使用默认图片模型。
- 视频生成优先使用用户选择的模型，未指定时使用默认视频模型。

### 3.2 试算接口

新增用户鉴权接口：

```text
POST /api/v1/points/quote
```

请求示例：

```json
{
  "business_type": "video_generation",
  "model_id": null,
  "duration_seconds": 10,
  "resolution": "1080p",
  "generation_count": 1
}
```

响应示例：

```json
{
  "resolved_model_id": "model-123",
  "resolved_model_name": "Veo 3",
  "using_default_model": true,
  "required_points": 200,
  "available_points": 300,
  "sufficient": true,
  "quote_token": "signed-short-lived-token"
}
```

`business_type` 决定允许的参数结构和模型类别，不能由前端直接传任意计费公式。

`quote_token` 使用服务端签名的短期凭证实现，至少包含当前用户 ID、`business_type`、解析后的模型 ID、计费参数哈希、`required_points` 和过期时间。建议有效期为 5 分钟。前端不能修改凭证内容，服务端无需为每次试算额外写数据库。

### 3.3 正式提交复算

前端正式提交时携带 `quote_token`，但不传入可信的最终扣费金额。后端必须：

1. 重新解析最终模型。
2. 按正式请求参数重新计算价格。
3. 对比试算中的模型、价格和参数。
4. 一致时进入冻结流程。
5. 不一致时返回 `POINTS_QUOTE_CHANGED` 和新试算结果，不调用供应商。

试算结果不能替代正式提交时的余额校验和计费计算。

## 4. 冻结与结算流程

### 4.1 统一流程

同步文本、异步图片和异步视频均使用同一套预扣费机制：

```text
解析最终模型与参数
  → 计算所需积分
  → 校验可用积分
  → 冻结积分并写 freeze 流水
  → 调用模型供应商
      ├─ 成功：冻结转消费，写 consume 流水
      └─ 失败/取消：释放冻结，写 unfreeze 流水
```

冻结成功是调用供应商的前置条件。任何积分校验或冻结失败都不得产生供应商请求。

### 4.2 状态变化

假设调用前：

```text
balance = 200
frozen = 20
available = 180
required = 100
```

冻结后：

```text
balance = 200
frozen = 120
available = 80
```

调用成功消费后：

```text
balance = 100
frozen = 20
available = 80
```

调用失败或取消解冻后：

```text
balance = 200
frozen = 20
available = 180
```

### 4.3 同步文本

同步文本调用在请求内完成完整生命周期：冻结后调用供应商；正常返回则立即消费；发生超时、异常或明确失败则立即解冻。

### 4.4 异步任务

图片和视频任务记录保存 `billing_id`。任务成功、失败和取消状态流转分别调用消费或解冻服务。

如果冻结成功但任务创建失败，创建流程必须立即解冻。不能留下没有业务任务关联的冻结积分。

### 4.5 超时补偿

补偿任务复用项目现有 Celery 体系，由 Celery Beat 每 5 分钟触发一次：

```text
backend/app/tasks/points.py
└── reconcile_stale_point_freezes       # Celery 定时任务入口

backend/app/services/points/reconciliation.py
└── reconcile_stale_freezes             # 查询、判断和结算逻辑
```

`app.core.celery_app` 注册 `app.tasks.points` 和 Beat schedule。部署环境新增一个且仅一个 Celery Beat 实例，避免多个调度器重复投递；即使发生重复投递，结算服务仍必须依靠幂等约束保证安全。

任务每次扫描超时未结算的 `freeze` 流水：

- 关联任务成功：补记消费。
- 关联任务失败或取消：执行解冻。
- 任务不存在且冻结超过 30 分钟：执行解冻并记录异常备注。
- 无异步任务关联的同步调用冻结超过 30 分钟：执行解冻。
- 任务仍在运行：保持冻结，等待下次扫描。

`pending` 或 `running` 状态不能仅因时间过长而解冻，避免供应商仍在执行时释放积分。补偿任务必须复用正常结算服务、Redis 用户锁、数据库事务和幂等约束，不能直接修改余额。

## 5. 并发与幂等

### 5.1 Redis 用户级原子锁

所有积分变更按用户加锁：

```text
points:user:{user_id}
```

锁要求：

- 使用唯一随机 token 标识持有者。
- 设置自动过期时间，避免进程异常形成永久死锁。
- 仅允许持有相同 token 的请求通过原子比较并删除脚本释放锁。
- 获取失败时进行有限次数、带退避的短暂重试。
- 重试耗尽返回明确的“积分操作繁忙”错误。
- 锁粒度为 `user_id`，不同用户积分操作可并行。

Redis 锁用于降低数据库争用，不作为最终一致性的唯一保障。

### 5.2 数据库事务和行锁

获得 Redis 锁后执行：

1. 开启数据库事务。
2. 使用 `SELECT ... FOR UPDATE` 锁定 `user_points`。
3. 锁定当前 `billing_id` 对应的冻结流水。
4. 校验余额、流水幂等状态及结算互斥状态。
5. 更新积分状态并追加流水。
6. 提交事务。
7. 释放 Redis 锁。

数据库事务、检查约束、唯一约束和行锁负责最终一致性。即使 Redis 锁过期或暂时不可用，也不能发生负余额、超额冻结或重复结算。

### 5.3 幂等规则

- 每次模型调用生成唯一 `billing_id`。
- 同一 `billing_id` 只能冻结一次。
- 同一冻结只能消费或解冻一次。
- `consume` 与 `unfreeze` 互斥。
- 重复成功、失败或取消回调返回已有结算结果，不重复修改余额。
- 任务取消和失败回调并发时，仅第一个完成结算的操作生效。

## 6. 充值规则

管理员充值复用同一接口和 `recharge` 流水类型：

- 正数表示增加积分。
- 负数表示扣减积分。
- 负数充值必须填写备注。
- 操作后 `available_points` 不得小于 `0`。
- 操作人写入 `created_by`，来源写入 `admin`。

管理员不能通过负数充值扣除已被冻结的积分。例如用户总积分为 `100`、冻结积分为 `80`，最多只能充值 `-20`。

未来自助充值仍写入 `recharge` 流水，通过 `source=self_service` 与管理员充值区分，无需新增流水类型。

## 7. Service 与 API 职责

### 7.1 Service 层

新增集中式积分服务，所有模型调用点显式接入：

```text
PointsService
├── quote()
├── calculate_cost()
├── freeze_for_llm_call()
├── consume_frozen()
├── unfreeze_frozen()
├── recharge()
├── get_user_points()
└── list_transactions()
```

集中式服务负责计费公式、模型解析协作、Redis 锁、数据库事务、幂等和流水。供应商适配器不直接操作积分。

不采用全局 Provider 拦截器，因为文本、图片、视频调用的计费参数和任务生命周期不同；业务 service 在已具备完整上下文的位置显式调用积分服务，更容易保证正确结算。

### 7.2 API 层

API 层只负责：

- 接收并校验请求。
- 鉴权及管理员权限校验。
- 调用 service。
- 将领域错误组织为稳定响应。

计费、余额变化和任务结算不得写在路由函数中。

### 7.3 建议接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `GET` | `/api/v1/points/me` | 用户 | 当前积分状态 |
| `GET` | `/api/v1/points/transactions` | 用户 | 当前用户流水列表与筛选 |
| `POST` | `/api/v1/points/quote` | 用户 | 模型调用前试算 |
| `GET` | `/api/v1/admin/users/{user_id}/points` | 管理员 | 查看用户积分 |
| `POST` | `/api/v1/admin/users/{user_id}/points/recharge` | 管理员 | 正数或负数充值 |
| `GET` | `/api/v1/admin/users/{user_id}/points/transactions` | 管理员 | 查看用户流水 |

模型管理的创建、更新和响应 DTO 增加 `unit_points`。

所有 API 变化落地后必须运行 `pnpm run openapi:update`，前端统一使用 generated client。

## 8. 错误契约

### 8.1 积分不足

正式调用时积分不足，不调用供应商：

```json
{
  "code": "INSUFFICIENT_POINTS",
  "message": "可用积分不足",
  "available_points": 80,
  "required_points": 120,
  "shortfall_points": 40
}
```

### 8.2 试算变化

```json
{
  "code": "POINTS_QUOTE_CHANGED",
  "message": "模型或价格已变化，请确认最新积分消耗",
  "quote": {
    "resolved_model_id": "model-456",
    "required_points": 160,
    "available_points": 200,
    "sufficient": true,
    "quote_token": "new-token"
  }
}
```

### 8.3 操作繁忙

Redis 锁有限重试失败时返回稳定错误码 `POINTS_OPERATION_BUSY`。前端可提示稍后重试，不应绕过计费继续调用供应商。

## 9. 前端交互

### 9.1 调用前展示

当模型、视频分辨率或视频时长变化时，前端重新调用试算接口。首期图片只有一个规格，不需要因图片分辨率触发试算。

展示位置遵循当前页面布局：

- 优先放在执行按钮附近，显示“将消耗 120 积分”。
- 如果现有按钮具备稳定宽度和辅助信息结构，可显示“生成 · 120 积分”。
- 不为统一位置而破坏现有页面视觉层级。
- 试算加载期间禁用执行按钮，避免用旧价格提交新参数。
- 积分不足时显示“可用 80，本次需要 120”，并禁用按钮。

前端禁用只改善体验，后端正式提交仍必须重新校验。

### 9.2 模型切换

图片或视频模型选择变化后立即重新试算。使用默认模型的页面传 `model_id: null`，并展示试算响应中的 `resolved_model_name` 和积分。

### 9.3 积分页面

用户端展示：

- 总积分。
- 冻结积分。
- 可用积分。
- 消费和充值明细。
- 按流水类型和时间筛选。

管理端用户列表或详情展示相同积分摘要，并提供正数/负数充值入口。负数输入时备注为必填项。

## 10. 接入边界

只接入实际产生模型供应商调用的入口，包括但不限于：

- 同步文本模型调用。
- 异步文本模型任务。
- 图片生成与图片编辑。
- 视频生成。
- 其他确实调用 LLM 或生成供应商的业务能力。

以下操作不计费：

- 提示词预览和本地渲染。
- 模型、供应商和项目配置 CRUD。
- 任务状态和结果查询。
- 素材、资产和分镜的普通编辑。
- 不产生供应商调用的本地计算或数据编排。

实施阶段必须枚举并审计实际供应商调用点，避免只按 API 路径名称判断是否收费。

## 11. 验收标准

- 每个文本、图片和视频模型均可配置统一的 `unit_points`。
- 显式模型和默认模型均能获得正确试算结果。
- 前端切换模型或计费参数后能刷新“将消耗 X 积分”。
- 正式提交使用与执行请求一致的最终模型和参数重新计费。
- 积分充足时先冻结，再调用供应商。
- 积分不足时不调用供应商，并返回可用、需要和差额。
- 同步文本成功后消费、失败后解冻。
- 异步图片和视频成功后消费、失败或取消后解冻。
- 冻结成功但任务创建失败时立即解冻。
- 重复回调不会重复消费或解冻。
- 并发调用不能造成超额冻结、负余额或重复结算。
- Redis 锁使用持有者 token 原子释放，数据库仍提供最终一致性。
- 管理员可正数或负数充值，负数不能侵占冻结积分且必须填写备注。
- 模型价格修改不影响历史计价快照。
- Celery Beat 每 5 分钟触发补偿任务，且部署环境仅运行一个 Beat 实例。
- 超时补偿能处理终态任务、超过 30 分钟的无任务冻结和同步调用遗留冻结。
- API 变更后 OpenAPI 和前端 generated client 已同步。
- 后端相关测试、前端 `pnpm exec tsc --noEmit` 及积分关键流程测试通过。

## 12. 实施顺序建议

1. 数据库迁移与模型价格字段。
2. 积分领域模型、计费器、Redis 锁和事务服务。
3. 试算、余额、流水和管理员充值 API。
4. 文本、图片、视频真实供应商调用点接入。
5. 异步任务结算与超时补偿。
6. OpenAPI generated client 同步。
7. 管理端和用户端积分界面。
8. 各模型调用界面的试算展示与不足拦截。
9. 并发、幂等、失败回滚和端到端验证。
